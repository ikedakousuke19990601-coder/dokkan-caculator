# ドカバト 被ダメージ計算ツール アーキテクチャ設計書（MVP）

基にした資料: `spec.md`

## 1. システム全体像（概要と基本方針）

### 構造のタイプ
**サーバーなしの静的SPA（シングルページアプリ）** にします。家づくりにたとえると、「1階建ての平屋で、玄関と居間だけがある家」です。

- すべての処理がユーザーのブラウザ内で完結する。計算もブラウザで行う
- サーバー、DB、ログイン、外部APIは一切ない
- 保存するのは前回の入力のみ（localStorage）で、外部には送信しない（spec 9章）

### 基本方針
| 方針 | 設計への落とし込み |
|---|---|
| 計算ロジックとUIの分離（spec 2章） | 計算は「入力を渡すと数値を返すだけの純粋関数」にする。Reactを一切importしない |
| 将来のスマホアプリ化 | 純粋関数をそのまま流用できるようにする。UIだけ作り直せばよい |
| リアルタイム更新 | 入力のたびに再計算する。計算は軽く、ボタンは不要 |
| 計算式が未確定（spec 7章） | 端数処理など変わりうる部分を1か所に隔離し、後から差し替えやすくする |

```
┌─────────────────── ブラウザ ───────────────────┐
│  UI層 (React)                                   │
│   入力フォーム ──→ 状態(state) ──→ 結果表示     │
│                      │  ▲                       │
│                      ▼  │                       │
│  ロジック層(純粋関数) calcDamage(input)         │
│                      │                          │
│  保存層  localStorage ◀─┘（前回の入力のみ）      │
└─────────────────────────────────────────────────┘
        ▲ 配信のみ：静的ファイルをホスティングから取得
```

## 2. 推奨する技術スタック

| 領域 | 採用 | 理由 |
|---|---|---|
| 言語 | **TypeScript** | 入力の型（区分・係数など）を明確にでき、計算式の取り違えをコンパイル時に防げる |
| フロントエンド | **React + Vite** | 入力に応じた再描画が得意。行の追加・削除（「これから上がる効果」）の状態管理が書きやすい。ReactならReact Nativeでスマホアプリ化しやすい |
| スタイル | **Tailwind CSS** | スマホ幅対応（レスポンシブ）が少ない記述で済む |
| バックエンド | **なし** | 要件上、サーバー処理がない。作らないことが一番安全で安い |
| データベース | **なし（localStorageのみ）** | 保存対象は前回の入力だけ |
| テスト | **Vitest** | 受け入れ基準(a)「手計算の期待値と一致」を自動テスト化する |
| ホスティング | **Vercel または Cloudflare Pages（無料枠）** | 静的ファイルの配信だけで足り、GitHub連携で自動デプロイできる |

**Next.jsを選ばない理由**: サーバー側レンダリングやAPIが不要で、機能過多になるためです。
**スマホアプリ化の道筋**: まずPWA化（ホーム画面追加）を試します。ネイティブが必要になったらReact Native（Expo）にし、`logic/` をそのまま共有します。

## 3. コンポーネント構成と役割分担

### ディレクトリ構成（部屋割り）
```
src/
├─ logic/                  ← 計算の部屋（UI非依存・ここだけ単体で動く）
│   ├─ types.ts            入力・出力の型定義
│   ├─ rounding.ts         端数処理（仮仕様をここに隔離）
│   ├─ calcDef.ts          現在DEFの計算
│   ├─ calcDamage.ts       被ダメージ計算（r=1.00 / 1.03）
│   └─ *.test.ts           手計算の期待値によるテスト
├─ storage/
│   └─ inputStorage.ts     localStorageの読み書き（失敗時も落ちない）
├─ components/             ← 画面の部屋
│   ├─ DefSection.tsx      A. 自分のDEF
│   ├─ EffectRow.tsx       「これから上がる効果」1行（区分＋％）
│   ├─ EnemySection.tsx    B. 敵の攻撃
│   ├─ ResultPanel.tsx     2つのダメージ値を表示
│   └─ Disclaimer.tsx      「目安」表示
├─ hooks/
│   └─ useCalcInput.ts     状態管理＋保存＋再計算をつなぐ
├─ App.tsx
└─ main.tsx
```

### 役割分担
| 部屋 | 役割 | 守るルール |
|---|---|---|
| logic | 数式の実装のみ | React・localStorage・DOMに触れない。同じ入力なら必ず同じ出力 |
| storage | 前回入力の保存・復元 | 壊れたデータや保存不可（プライベートモード等）でも既定値で起動する |
| hooks | UIとlogic/storageの橋渡し | 入力変更 → 保存 → 再計算 |
| components | 表示と入力の受け取り | 計算式を一切持たない |

### 主要な型（イメージ）
```ts
type EffectCategory = 'passiveAdd' | 'passiveMul' | 'support' | 'active' | 'superAttack'; // ④-足 ④-掛 ⑤ ⑥ ⑧

type DefEffect = {
  id: string;
  category: EffectCategory;
  addPercent: number;        // これから上がる％
};

type CalcInput = {
  screenDef: number;
  effects: DefEffect[];
  appliedPercent: Record<EffectCategory, number>;  // 反映済み％（通常0、「詳細」で入力）
  enemyAtk: number;
  reductionPercent: number;  // ダメージ軽減率
  attrGuardA: 1.0 | 0.9 | 0.8 | 0.7 | 0.6;
  allAttrGuardB: boolean;    // true → 0.5
  fieldCorrection: number;
};

type CalcResult = { noRandom: number; maxRandom: number }; // r=1.00 / r=1.03
```

## 4. データ設計・データフロー

### データ設計
DBはありません。保存するのは `CalcInput` のJSON 1件のみです。

| 項目 | 内容 |
|---|---|
| 保存先 | localStorage |
| キー | `dokkan-damage-calc:v1`（形式を変えたら `v2`にする） |
| 内容 | `CalcInput` |
| 復元時 | JSONを検証し、不正なら既定値にフォールバックする |
| 外部送信 | なし |

### データフロー
```
① ユーザーが入力（例: 敵ATKを変更）
② useCalcInput が state を更新
③ ├─ storage に保存（入力が止まってから約300msで保存。毎キー入力では書かない）
   └─ calcDamage(state) を呼ぶ
④ calcDef: 画面のDEF × 区分ごとの Π(1+反映済み+追加合計)/(1+反映済み)
   → 現在DEF（途中は都度切り捨て）
⑤ calcDamage: r=1.00 と r=1.03 の2通りで
   {敵ATK×r×A×(1−軽減率) − 現在DEF}×B×フィールド補正 → max(0, …) → 最終のみ四捨五入
⑥ ResultPanel が2つの数値を表示
```

### 計算実装で押さえる点
- 同じ区分の行が複数ある場合は、追加％を**合算してから1回だけ**掛ける
- ④パッシブは足し算枠と掛け算枠を**別の2つの区分**として扱う（spec 4章）
- 反映済み％が -100% のときは0除算になるため、入力値を検証してエラー表示にする
- 数値入力は空欄・負数・全角などを正規化し、`NaN` を結果に出さない
- 端数処理は `rounding.ts` に集約する。ダメージ側は仮仕様のため、検証後はここだけ直せばよい

## 5. 非機能要件への配慮

| 観点 | 対策 |
|---|---|
| セキュリティ | サーバー・ログイン・個人情報がなく、攻撃対象が小さい。外部送信なし。localStorageの読み込みはJSON検証してから使う。HTTPS配信（ホスティングが標準対応） |
| パフォーマンス | 計算量は数十回の四則演算で、再計算は一瞬。Reactと数コンポーネントだけなので初回読み込みも軽い。「入力→結果」の遅延はない |
| 使いやすさ（受け入れ基準c） | 必須入力は敵ATKと画面のDEFのみ。区分は2行をあらかじめ表示。反映済み％は「詳細」に隠す。前回入力を復元して再入力を減らす |
| レスポンシブ | モバイルファーストで設計。入力は `inputMode="numeric"` にしてスマホで数字キーを出す |
| 対応ブラウザ | 最新のChrome・Safari。オフライン対応はしない（spec 9章）ので、Service Workerは入れない |
| 保守性・拡張性 | 計算ロジックの分離＋単体テスト。式の変更点（端数処理・属性相性）は `logic/` 内で完結。属性相性など「含めないもの」を後で足す場合は、`CalcInput` に項目を足し、`calcDamage.ts` に段を足す形で拡張できる |
| 正確性 | 手計算の期待値をテストケースにして回帰を防ぐ。画面に「目安」の注記を常時表示する |

## 6. 今後の開発ステップ

安全な順番は「**計算ロジック → 最小のUI → 保存 → 磨き込み**」です。

| ステップ | 内容 | 完了の目安 |
|---|---|---|
| 0. 準備 | Vite＋React＋TS＋Tailwind＋Vitest の雛形を作成し、GitHubとホスティングを連携 | 空の画面が公開URLで見える |
| 1. 計算ロジック | `logic/` を実装し、手計算の期待値でテスト（区分の合算、反映済み％、軽減率、A/B係数、max(0)） | **受け入れ基準(a)をテストで満たす** |
| 2. 最小UI | 画面のDEF・敵ATK・結果2つだけの画面。入力でリアルタイム更新 | 基本ケースが画面で計算できる |
| 3. 入力の拡充 | 「これから上がる効果」の行追加・削除、軽減率、属性防御A/B、フィールド補正、「詳細」（反映済み％） | specの全入力項目が揃う |
| 4. 保存 | localStorageへの保存・復元（壊れたデータへの対処つき） | リロードしても前回の入力が残る |
| 5. 仕上げ | スマホ幅の確認、Safari確認、「目安」表示、入力エラー表示 | 実機のSafari・Chromeで操作できる |
| 6. 公開 | 本番デプロイ。公開して使い始める | URLで利用できる |
| MVP後 | 実機検証（受け入れ基準b）→ 端数処理を確定。必要に応じて属性相性・見切り・気力、PWA化、スマホアプリ化 | spec 7章の未確認事項が解消 |

### 最初の着手点
**ステップ1（計算ロジック）から始めるのが最も安全**です。ここが全体の正しさを決め、UIに依存せず単体でテストできます。仕様に未確認の部分（端数処理）があるため、まず仮仕様で実装し、実機検証後に `rounding.ts` だけを直します。

## 7. リスクと留意点

| リスク | 対応 |
|---|---|
| 計算式が公式非公開で、誤差が出る可能性 | 「目安」表示と、実機検証後の式の見直し |
| ダメージ側の端数処理が未確認 | `rounding.ts` に隔離し、テストの期待値も合わせて更新できるようにする |
| 属性相性が計算順序に影響する可能性（未検証） | MVP後に実機で検証し、必要なら `calcDamage.ts` の順序を見直す |
| 掛け算パッシブの判別に例外あり | 区分はユーザーが選ぶ方式なので、MVPでは例外をユーザー判断に任せる |
